# 输出资产体系：三个文件，各司其职

> 实现：`Code/src/geom/asset.py`（schema + 生成 + 自检）、`Code/render/render_asset.py`（.blend + 预览图）
> 测试：`python Code/tests/test_asset.py`（11 项）
> 上游：`docs/11_物体输入管道.md`

## 1. 直接回答

一条命令，一个**自包含的案例目录**，里面三个文件，角色不可互换：

```bash
python Code/scripts/analyze_object.py part.obj --mass 2.5 --out-dir results/
```

```
results/
└── part/
    ├── input/
    │   ├── part.obj          源文件副本（案例可独立带走）
    │   └── request.json      输入卡：质量/密度、随机种子、凸包上限、可重放命令
    └── output/
        ├── part.asset.json   数据：唯一真值，机器读、可 diff（不含网格顶点）
        ├── part.blend        资产：渲染网格 + 碰撞代理 + 质心/主轴标记
        └── part.preview.png  证据：QA 板，核对"数字和形状是否对得上"
```

`input/` 与 `output/` 的分工是一句话：**`input/` 说"我要什么"，`output/` 说
"算出了什么"**。后者全是算出来的，能从数据反推；前者有几个自由度反推不回来
（见下节），所以必须单独记。

### 为什么按物体分目录，而不是按文件类型分

按类型分（所有 json 一堆、所有 png 一堆）时，想看某个物体做了什么，要在三个目录
之间来回找；而且**删掉一个物体要在三个地方各删一次**，漏一个就留垃圾。

按物体分则每个案例自包含，代价是同类产物散落各处——所以内部分 `input` / `output`
两层，把"进来的"和"算出去的"隔开。

`input` 不是中间产物，是**证据链的一环**：`source.sha256` 校验的对象就在它旁边，
一年后还能确认这份资产是从哪个文件、哪个版本算出来的。所以命令会把源文件
**复制**进去（不是移动——原文件可能被别的东西引用），并让 `source.path`
指向副本，换台机器也能自证。

**为什么不是两个、也不是四个**：这三个恰好对应三种消费者，少了任何一个都会有人
被迫去"猜"或"重新解释"：

| 文件 | 消费者 | 少了它会怎样 |
|---|---|---|
| `.asset.json` | 物理引擎、脚本、版本库 | 每个消费者自己算一遍，数字开始分叉 |
| `.blend` | 美术、渲染、人工检查 | 只能看数字，无法确认它对应什么形状 |
| `.preview.png` | 人（一眼） | 打开 Blender 才能发现"主轴装反了" |

## 2. 为什么不是 `.jpg`，也不是 `.glb`（但 GLB 可以可选）

**`.jpg` 不能当资产。** 它是一个截图，丢掉了结构、坐标、层级——除了"好不好看"
之外提供不了任何可执行的信息。它只能当**证据**，这也是它在第三个位置上的作用，
而且它应该是 PNG（无损，线框与文字不会被振铃糊掉）。

**`.glb` 比 `.blend` 差在丢结构。** glTF 是给"一个物体一个网格"设计的，而这个
资产的核心恰恰是**双表示**：一个渲染网格（高精度、可能带材质）+ 一个碰撞代理
（粗、低面数、独立、线框）。glTF 能塞两个 mesh，但塞不下：

- "哪个是碰撞、哪个是渲染"的语义（节点名是人读的约定，不是 schema）
- 质心与主轴的标记物（glTF 有节点但没有可视化约定）
- 资产摘要自定义属性

而且这个项目已经强依赖 Blender（渲染层就是它），所以 `.blend` 的边际成本是零。

### 可选的第四件产物：`--glb`

GLB 的问题只在于"不能当资产"，不在于"没有用"。它是唯一能在编辑器里**自由旋转**
查看的形式（`.blend` 要开 Blender，PNG 是固定视角），所以做成**显式开关**：

```bash
python Code/scripts/analyze_object.py Code/assets/prism.obj --mass 3.0 \
    --out-dir results/w3 --glb
```

**它不进默认流程。** 理由：`output/` 里每个文件都该有明确消费者，而 GLB 的消费者
是"人 + 外部工具"，不是求解器——默认生成只会多一个没人读的文件。

导出内容与取舍：

| 项 | 是否导出 | 原因 |
|---|---|---|
| 渲染网格、碰撞线框、质心、主轴 | ✅ 共 12 个节点 | 这三样正是要看的 |
| `label_X/Y/Z` 文字标签 | ❌ | 朝向相机的广告牌，自由旋转时立刻变成"贴在屏幕上"的怪东西 |
| 相机、灯光、地面 | ❌ | 查看器自带环境，带过去只会打架 |

实测（`prism.glb`，157 KB）：

```json
节点: prism_render, prism_collision, COM,
      axis_X_shaft/head, axis_Y_shaft/head, axis_Z_shaft/head,
      axis_X_neg_shaft, axis_Y_neg_shaft, axis_Z_neg_shaft
材质: body  alphaMode=BLEND  baseColor=[0.34, 0.45, 0.66, 0.40]
      hull_wire  OPAQUE  baseColor=[1.0, 0.62, 0.10, 1.0]
```

`alphaMode=BLEND` 是这一条的关键：只设 Principled 的 Alpha 端口，Cycles 渲染是
透明的，但**导出的材质仍是 OPAQUE**，在查看器里就看不进物体内部——而"看进内部"
正是这张资产的用处。所以 `_set_alpha` 同时设 `material.blend_method = "BLEND"`，
glTF 导出器靠它决定 `alphaMode`。

**回灌验证**：把 `prism.glb` 重新导入 Blender、换一个 40° 斜视角渲染，12 个对象
齐全、半透明体、橙黄凸包线框、RGB 主轴都在，Z 轴朝上（glTF 的 Y-up 转换正确）。

## 3. JSON schema

顶层字段：

| 字段 | 内容 |
|---|---|
| `schema` | `"object_asset/1"`，消费者必须先校验 |
| `name` | 资产名，也是场景里的物体名 |
| `units` | `{length: "m", mass: "kg", angle: "rad"}` |
| `paths_relative_to` | 所有路径的基准目录，固定为 `"."`（= 本 JSON 所在目录） |
| `source` | 出处：路径、**sha256**、顶点/面数、闭合性与 χ、signed volume |
| `frames` | 两个坐标系与互转变换（见第 4 节） |
| `mass_properties` | 体积、质量、密度、表面积、**质心**、**完整 3×3 张量**、惯量积、非对角占比 |
| `principal` | **主惯量**、**主轴（按列存）**、四元数 |
| `collision` | 凸包点/面/棱、体积、填充比、SAT 候选轴数；点云输入时为 `null` |
| `render` | **网格引用（路径 + 顶点/面数）**、材质、地面 |
| `engine` | **引擎交接**：`inertia_local`、`orientation_offset`、`ground_z_offset` |
| `checks` | 自检结果（见第 6 节） |

`source.sha256` 是溯源关键：拿到 JSON 能确认它对应哪个版本的文件，
而不是"大概是最新那个 obj"。

### 为什么网格**不**内联

第一版我把顶点表直接塞进 `render.mesh.inline`，理由是"JSON 自包含"。这是错的：
几何已经在两处了——`input/` 里的源文件（原始、可追溯）和 `output/*.blend`
（可直接用）。再存一份就是**第三份重复**，而且它有具体代价：

- 一个 5 万面的模型会让 JSON 从 10 KB 涨到几 MB
- JSON 的本职是"数值与引用"，塞进几何之后就既不好读也不好 diff
- 三份副本一旦不同步，没人知道该信哪个

所以现在只存 `path` + 顶点/面数（**统计量用于校验引用没被换掉**）+
`frame`。自包含性由**目录**保证（`input/` + `output/` 一起搬），不靠单文件。

代价是路径必须相对化，否则换个工作目录就找不到文件。所有路径都相对于
`paths_relative_to`（=`output/`），所以 `source.path` 长这样：
`../input/prism.obj`。

### `input/request.json`：记产物反推不回来的输入

| 信息 | 为什么反推不回来 |
|---|---|
| `--mass` 还是 `--density` | 同一个网格给 3 kg 和给密度 1200 算出的惯量不同，但产物里只有一个质量数 |
| **随机点云的种子** | 点云文件能存下来，"它是怎么生成的"存不下来。`random:8000:7:1,1,1` 这一行才是完整信息 |
| 凸包面数上限 | 同一点集换个 `max_faces` 会得到不同代理 |
| 要求的修正式 | 资产里记了**结果**（`correction.mode`），记不了"我要的是 auto 还是强制 nn" |

格式是 `case_request/1`，含 `command`（可原样重放的命令行）、`inputs`、
`mass_spec`（并说明是"直接给定"还是"密度 × 体积"）、`geometry_spec`、
`correction_spec`。

这一条是被问出来的：`input/` 里原来只有几何文件，而**质量、随机种子这些
决定结果的自由度没有任何地方记录**。

## 4. 两个坐标系、两个四元数

这是整个 schema 里**最容易出错**的地方，所以它是一等公民。

```
source 系：输入文件自己的坐标
   │  p_body = R(source_to_body.rotation) @ (p_source + translation)
   ▼
body 系：原点在质心、坐标轴与惯量主轴重合
```

分工是明确的：

- **质量属性报在 `source` 系** —— 质心坐标、非对角惯量积只有在原坐标系里
  才有物理意义，也才能和 CAD 对照
- **碰撞几何报在 `body` 系** —— 引擎要的就是"质心在原点、轴与主轴重合"的姿态

### 两个四元数互为共轭

| 字段 | 值 | 用途 |
|---|---|---|
| `frames.source_to_body.rotation_wxyz` | $Q^{\mathsf T}$ | 把**点**转进 body 系 |
| `engine.orientation_offset_wxyz` | $Q$ | 并进**物体姿态** |

混用这两个，症状极具误导性：**顶点世界位置完全正确**（共轭把反射抵消了），
但世界逆惯量错到 7.24。我在凸包那一轮就是这么栽的。

所以 `checks` 里有一条专门验证它俩互为共轭（`frame_quaternions_conjugate`），
不是"顺手加的"，是对着真实 bug 加的。

## 5. 引擎交接：为什么只给三个数

```json
"engine": {
  "inertia_local": [0.212425, 0.295908, 0.328333],
  "orientation_offset_wxyz": [0, 0.622332, 0.782753, 0],
  "ground_z_offset": 0.3
}
```

引擎内部只存**对角**惯量。把主轴旋转并进姿态之后，

$$I_{world} = (R_{spec} \cdot R_{offset})\,\mathrm{diag}(\lambda)\,(R_{spec}\cdot R_{offset})^{\mathsf T}$$

依然成立，所以引擎的实现一行都不用改。这也是"完整张量"能落地的方式：
它不进入运行时，只进入**姿态的一个额外旋转**。

`ground_z_offset` 是 body 系最低点的相反数，直接当 `position.z` 用，
物体一加载就贴地静止（引擎的初始穿透校验会拒绝嵌入的场景，这不是可选项）。

## 6. `checks`：error 与 info 必须分开

自检结果带 `severity`，因为混在一起会让报告失真：

| severity | 含义 | 例子 |
|---|---|---|
| `error` | **某个数字不能用** | 体积非正、张量不可由 QΛQᵀ 重构、网格不闭合 |
| `info` | **形状的性质**，不是故障 | 有凹陷所以凸包偏大、非对角占比大所以不能用对角近似 |

实测那个空心盒的资产：

```
自检：8 项全部通过
  · collision_is_exact: 凸包/本体 = 1.782455  ← 有凹陷，碰撞代理偏大
```

凸包比本体大 78% 不是 bug，是**空心**这个事实的定量表达（外盒 1.0 m³，
材料只有 0.561 m³）。如果它被印成 `✗`，人会去修一个不存在的问题。

八条检查：`principal_axes_orthonormal`（含 det = +1）、`tensor_reconstruction`、
`frame_quaternions_conjugate`、`volume_positive`、`mesh_closed`、
`collision_is_exact`、`diagonal_approximation_safe`、`ground_offset_nonnegative`。

`det = +1` 那条不是形式主义：Jacobi 的特征向量符号任意，**约一半概率给出
左手系**（实测随机 200 个对称阵有 97 个 det = −1）。那对"重建张量"毫无影响，
但它是**反射不是旋转**，转四元数就崩。

## 7. 闭合：资产 → 场景 → 引擎

```python
spec = asset_to_object_spec(asset)   # 资产 → 场景物体
```

场景物体从资产派生，所以**不会出现两份数字打架**；资产改了，场景跟着变。
`emit_scene` 就是用它实现的。

`test_object_spec_roundtrip_to_engine` 是这条闭环的验收：资产 → 场景 JSON →
`PhysicsWorld` → 跑 3 秒，要求主惯量与资产一致（`< 1e-9`）、静止、最低点
落在 ±2 mm 内。只验证"JSON 写出来了"是不够的。

## 8. `.blend` 里有什么

```
prism_render      渲染网格（半透明，来自 inline）
prism_collision   碰撞代理（黄色线框圆柱 + 顶点小球，已 join）
COM               质心（白色小球，在世界原点）
axis_X/Y/Z        主轴箭头（红/绿/蓝 + 反向短轴 + 文字标签）
Camera / key / fill / Ground
```

**全部在 body 系**。渲染网格本来是 `source` 系的，这里做了变换——
如果直接原样摆进去，两者会错开一个"质心平移 + 主轴旋转"，
而那正是最需要被这张图检出的错误。

地面放在 `z = -ground_z_offset`，物体贴地，同时 body 原点仍留在世界原点。

场景自定义属性带着出处：`schema`、`name`、`mass`、`volume`、
`center_of_mass_source`、`principal_moments`、`orientation_offset_wxyz`、
`ground_z_offset`、`coordinate_frame`。所以 `.blend` 自己也能被审计。

## 9. 预览图看什么

它不追求好看，四件事必须一眼可判：

1. **三条轴是否交于质心**（白色小球）—— 交点不在球上就是 body 系定义错了
2. **凸包线框是否包住网格** —— 空心盒那张图里，线框贴外表面而材料只有一层壳，
   比值 1.78 就写在 JSON 里
3. **轴的朝向是否合理** —— 主轴必然穿过最长的/最短的方向；不对称物体一眼能看出
4. **没被裁** —— 相机按包围半径自动取景（`distance = 3.9 × radius`）

半透明是必要的：主轴与质心在物体**内部**，不透明的话会被完全挡住，
而它们是否穿过质心恰恰是要核对的东西。

### 一个必须关掉的 Blender 默认行为

Blender 覆盖保存时会生成 `<name>.blend1` 备份。在 `output/` 里它就是一份
无意义的 800 KB 垃圾，而且**每重跑一次多一份**。`render_asset.py` 在保存前
设 `preferences.filepaths.save_version = 0`。

这个坑是实测目录时发现的：第一版 `results/w3` 里躺着 `prism.blend1`，
和 `prism.blend` 一模一样大。

同样的输入永远产出同样的字节，diff 里只会有真正的改动。

## 12. 场景资产 `scene_asset/1`：只有引用

装配命令：

```bash
python Code/scripts/assemble_scene.py --root results/w3 --name stack \
    --place shell=0 --place prism=1.05 --emit-engine out/stack.engine.json
```

```
results/w3/stack/
├── input/    request.json   装配配方（可重放）
└── output/   stack.scene.json     场景资产，约 2.4 KB
              stack.engine.json    展开后的快照（给引擎，明确不是真值）
```

场景条目的全部内容：

```json
{"name": "prism",
 "asset": "../../prism/output/prism.asset.json",
 "asset_sha256": "…",
 "transform": {"position": [0.0, 0.0, 1.35], "orientation": [0, 0, 0, 1]}}
```

**没有质量、没有惯量、没有凸包、没有材质（除非场景要覆盖）。**

### 为什么不能复制

这是被明确要求的，而且理由可以量化。假设 20 个物体，每个内联自己的凸包点集
（典型 26 个点 × 3 个 double ≈ 600 B）+ 质量属性 + 材质 ≈ 2 KB：

| 方案 | 体积 | 物体改动后 | 出错时 |
|---|---:|---|---|
| 复制 | ~40 KB+，且有大量重复 | **场景不跟着变**，两份数据分叉 | 不知道该信场景还是信物体 |
| **引用** | **~3 KB** | 场景立刻反映新值 | 唯一真值，无需判断 |

分叉是最严重的一条：它不是"多占点空间"，而是**产生一个静默的错误版本**。
物体重新算过、场景还拿着旧数字，仿真出来的结果是错的，但没有任何东西报错。

所以 `build_scene_asset` 有一条**结构约束**：物体条目里出现
`mass_properties` / `principal` / `collision` / `geometry` / `mass` 任一字段，
自检项 `no_inlined_object_data` 立刻失败。这条检查是设计约束的守门人。

### 指纹解决"引用会过期"

引用方案唯一的风险是：物体资产改了，场景还指向它，而场景的意图是旧版本。
所以每条引用带 `asset_sha256`，自检项 `asset_fingerprints_match` 会比对。
指纹不一致意味着**场景需要重新生成**，而不是"引用坏了"——这个区别对使用者
很重要。

### 相对路径解决"搬不走"

`asset` 写成 `../../prism/output/prism.asset.json`，所以整个 `results/` 换台
机器仍然成立。这也是为什么路径基准（`paths_relative_to`）必须显式声明：
解析规则只有一套，不留给每个消费者自己猜。

### 直连仿真：不必先生成快照

```bash
python Code/scripts/run_sim.py --scene-asset results/w3/stack/output/stack.scene.json \
    --out results/w3/stack/output/stack.poses.json --render
```

物理侧直接解析引用，**没有中间文件**。只有渲染前才展开一次，因为 Blender 层
（`render_anim.py`）需要自包含的场景；展开结果叫 `*.expanded.scene.json`，
每次都重新生成、绝不复用——复用旧快照就会"用旧物体渲染新场景"。

展开逻辑只有一处（`scene_asset_to_scene_dict`），`run_sim.py` 与
`assemble_scene.py` 共用，所以手工导出与直连仿真不可能展开出两种结果。

### `--emit-engine` 是快照，不是资产

展开后的 `stack.engine.json` 把引用替换成实体，给引擎加载用。它明确标注
"不是真值"：一旦物体资产更新，这份快照就过期了。区分这两者是必要的——
把快照当真值，就又回到了"复制"那套问题。

### 摆位的语义陷阱

`--place name=z` 里的 `z` 是**底面离地高度**（`0` = 贴地），不是质心高度。

我第一版按质心高度实现，`--place shell=0` 让一个 1 m 高的盒子有一半埋在土里，
引擎直接拒绝：

```
- 地面 <-> 'shell'：初始穿透 480.000 mm
```

这正是那道初始穿透校验存在的意义。改成"底面离地高度"后没有歧义：`0`
永远等于"放上去"。转换在写场景时一次完成（加上各物体的 `ground_z_offset`），
**场景里存的仍是质心位置**，与引擎语义一致，没有隐藏约定。

## 13. 一个差点被漏掉的缺陷：惯量只走到了 JSON 门口

这是本轮最重要的发现，而且只有**空心**物体能暴露它。

### 症状

场景装配后的自检报：

```
主惯量 vs 物体资产  最大相对差 = 2.48e-01
```

24.8%。对棱柱是 0，对空心盒是 24.8%。原因在引擎：

```python
# body.py，改之前
inertia = compute_inertia(spec.geometry, spec.mass)
```

`RigidBody.from_object_spec` **无条件从碰撞几何反推惯量**。而空心盒的碰撞
代理是实心外包盒（凸包/本体 = 1.782），从它反推的惯量自然偏大——差 24.8%
恰好是"质量分布被丢掉"的那个量，而且**提高精度也不会消失**。

换句话说：资产里算准了主惯量，写进了 JSON，但从没进过求解器。
整个"双表示"设计的意义（碰撞代理可以粗糙、质量分布必须精确）在最后一步失效。

棱柱看不出问题，因为它的凸包就是本体，两条路给出同一个答案。**这就是它
藏得住的原因**：最常用的样例恰好是唯一看不出来的形状。

### 修法

不是改引擎的算法，而是补一条通路：

1. `ObjectSpec` 增加可选字段 `inertia`（局部坐标系的三个对角元）
2. `from_object_spec` 有显式值时直接用它，**且不再叠加 `inertia_frame()`**
   ——资产里的主惯量本就相对"质心在原点、轴与主轴重合"给出，而碰撞点也存在
   同一坐标系里，两者已对齐；再转一次就转多了
3. `asset_to_object_spec` 把 `principal.moments` 写成 `inertia`（真字段，
   不再是 `_` 前缀的注释）

修完后同一场景的自检是 `0.00e+00`，逐位一致。

### 为什么这条值得单独写一节

它说明**"数据算对了"和"数据到位了"是两件事**。资产的 16 条测试里，
第 6 条（资产 → 引擎主惯量一致）此前用的是棱柱——恰好是两条路径重合的形状，
所以它以 1e-9 通过，却掩盖了通路缺失。现在第 14 条专门用空心盒，
并且先断言 `凸包/本体 > 1.5`，确保这条测试测得到东西。

## 14. 可复现性校验：把声明变成断言

`input/request.json` 里写着 `command`、种子、`max_faces`，但那只是一句话。
`Code/scripts/reproduce.py` 把它变成证明：

```bash
python Code/scripts/reproduce.py --root results/w3
```

做法是**执行记录下来的那条命令**（不是另写一遍等价流程——那种等价流程迟早会
和真入口分叉，于是测试永远绿），把路径前缀改写到临时目录，然后与 `output/`
里的产物逐字节比对。场景案例还会用重放出的场景资产再跑一遍仿真，
比对 `*.poses.json`——这一步验证的是**求解器确定性**。

### 它是规格的审查者，不是脚本的测试

输入卡漏记任何一个能改变结果的自由度，重放出的产物就会不同。它已经抓到一个：

装配命令记录里漏了 `--emit-engine` 与 `--duration`，于是重放不产出引擎快照。
表面上是"重放脚本不够聪明"，实际上是**输入卡没记全**——补在记录侧才对，
补在重放侧就是掩盖。

### 一个假阳性，比不测更糟

第一版把 `output/` 也复制进临时目录，于是比对变成了"副本 vs 原件"，
永远相等。`stack.poses.json` 明明没被重放也报"一致"。

修法是让 `output/` **从空开始**：这样"临时目录里存在某个产物"本身就证明是这次
重放生成的。同时只复制 `input/`，顺带避开几百 MB 的 `.blend/.png/.mp4`。
