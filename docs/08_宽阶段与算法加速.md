# 宽阶段：空间哈希与算法加速

> 实现：`Code/src/physics/broadphase.py`
> 测试：`python Code/tests/test_broadphase.py`（9 项）
> 基准：`python Code/scripts/bench_broadphase.py`（约 19 秒）
> 演示：`results/w2/demo_pile.mp4`（58 帧 / 24 fps / 2.4 s）

## 1. 问题

窄相（球-球、球-盒、盒-盒）逐个物体对都很便宜，但**枚举所有物体对**是 O(N²)：

$$N=400 \Rightarrow \frac{400 \times 399}{2} = 79{,}800 \text{ 对/次检测}$$

而每秒要检测 `24 帧 × 3 子步 = 72` 次（TOI 分段时更多）。实数接触的物体对通常只有
O(N) 量级，其余全是白算。

宽阶段要做的就是：**用廉价的包围盒先筛掉绝大多数明显不相交的对。**

## 2. 两个实现，一个用来跑、一个用来比

| 类 | 作用 |
|---|---|
| `SpatialHashBroadphase` | 均匀网格空间哈希，实际使用 |
| `BruteForceBroadphase` | O(N²) 枚举，**只用于提供加速比基线** |

保留基线不是冗余。**没有基线的"优化"无法证明有效**，也无法说明优化在哪里生效。
代价是几十行代码，收益是整份加速比表格。

## 3. AABB 必须按朝向算

这是最容易写错的地方。盒子的世界 AABB **不能用局部半尺寸**：

$$\text{extent}_k = \sum_i \left|a_i[k]\right| \cdot h_i,\qquad a_i = R\,e_i$$

一个 45° 倾斜的单位立方体，世界 AABB 的半宽是 √2/2 ≈ 0.7071 而不是 0.5——
**用局部半尺寸会小 30%，直接漏掉大量真实接触**，症状是小球穿过斜放的盒子。

测试第 2 项专门验证这一点：

```
正放半宽=0.500000（期望 0.5），倾斜 45° 半宽=0.707107（期望 0.707107）
```

## 4. 空间哈希的实现要点

### 4.1 格子边长

$$\text{cell} = 2 \times \overline{r_{\text{bound}}},\qquad r_{\text{bound}} = \text{包围球半径}$$

用**平均值**而不是最大值，是为了让少数几个大物体不至于把整张网格撑粗——
大物体另有兜底通道。取物体直径的量级是经验值：太小会让物体跨很多格子，
太大则每格塞满物体、剔除率下降。

### 4.2 大物体兜底通道

一个 20 m 见方的地面如果格子边长是 0.25 m，它要占 80×80×1 = 6400 个格子。
**插入开销会压过剔除带来的收益。**

所以设了一个上限（64 格）：跨格超限的物体放进 `_large` 列表，
之后每个物体都与它单独比较一次。这条通道把"大物体"的复杂度从
"格子数爆炸"降回 O(N)，代价是它对所有物体都变成候选。

**这条通道在正常场景里永远不触发**，所以必须单独测——写错了会静默漏掉大物体
与所有物体的接触，症状是"小球穿过大平面"，而且只在尺寸悬殊时出现。

### 4.3 输出必须排序

哈希表的遍历顺序依赖插入顺序。如果直接返回，求解器的接触处理顺序会随物体数量浮动，
同一场景在不同规模下给出略有差异的结果——**对可复现性是致命的**，也让加速比对照失去意义。

所以返回前统一 `sorted()`。

### 4.4 为什么用均匀网格而不是八叉树

八叉树需要维护层级、插入删除、节点分裂合并，代码量是三到五倍。物体分布比较均匀时
（本项目的堆叠、散落场景），均匀网格的剔除率已经很好，而且实现简单、缓存友好、
每帧可以直接清空重建。

## 5. 正确性判据

宽阶段的判据很特殊：**它为了性能本来就会漏掉绝大多数对。**

所以不能问"哈希和暴力结果一样吗"——那等于"不许优化"。正确的判据是：

> **哈希结果 == 所有 AABB 相交的物体对**

- **不漏**：AABB 相交是窄相接触的**必要条件**，保证这条就不会漏接触
- **不虚增**：结果必须是暴力枚举的子集，否则白跑窄相

测试第 3 项直接验证这个等式：

```
120 组随机场景，共 658 个相交对，完全一致
```

第 4 项验证格子边长在 0.08–3.0 m 七档下结果都相同（防"靠运气才没漏"），
第 7 项验证两种宽阶段产出的**接触流形集合完全相同**。
第 9 项验证地面接触不受影响——地面是无限平面，塞不进网格，走独立的 O(N) 通道，
这条测试防止将来有人"顺手"把它也塞进网格里。

## 6. 一个方法论错误：不公平的比较

第一版基准脚本只比"宽阶段自身耗时"，结果哈希**看起来慢了 10 倍**：

```
N=20   暴力 7.77us   哈希 87.40us   0.09x
```

这个结论完全是假的。原因：

> 暴力宽阶段做的事只是**生成 N(N-1)/2 个下标对**——它不做任何实际判断，
> 全部开销都推给了窄相。所以它的"自身耗时"几乎为零。

拿"几乎为零"去比"哈希的建表开销"，等于说"什么都不做比做点事更快"。
**公平的对比必须把下游的窄相开销一起算进来。**

修正后主指标改为「检测耗时 = 宽阶段 + 窄相」，结论立刻反转。
这一条记在这里，因为它是做性能对照时最容易犯、也最容易被误信的错误。

### 7.3 怎么读这两张表

**必须如实说明的三点：**

1. **N=20 的密集场景下哈希确实更慢（0.60×）。** 建表与 AABB 计算的开销压不过
   只减少 1.9 倍的候选对。这不是缺陷，是固定开销——它不是免费的，只是**增长得慢**。
   交叉点在 N ≈ 30。
2. **spread 的加速比是上限，不是典型值。** 物体真的散开时才有 45×；
   真实堆叠只能拿到 8×。
3. **对外汇报应引用端到端数字**（最后一列），它才是用户能感知的收益。
   检测加速比只说明算法本身的效果。

## 8. 演示场景

`results/w2/demo_pile.mp4` — 58 帧 / 960×540 / 24 fps / 2.4 s

一个 1.7 m 见方的静态盒容器，52 个球与盒子从上方落入并堆成 2–3 层。

| 指标 | 数值 |
|---|---|
| 物体总数 | 56（52 动态 + 4 静态墙） |
| 宽阶段自动格子 | 0.4704 m |
| 候选对峰值 | **146** |
| 暴力对数 N(N−1)/2 | **1 540** |
| 窄相调用减少 | **10.5×** |
| 物理耗时 | 576 步 / 124.7 s（0.217 s/步） |
| 终态最大速度 | 0.447 m/s（仍有小球在缓慢滚动） |
| 终态最大穿透 | 1.27 mm |

这个场景同时覆盖了三种碰撞组合：球-球（球之间）、球-盒（球撞墙、球撞盒）、
盒-盒（盒子互相压住、盒子压墙），所以它既是宽阶段的演示，也是盒-盒 SAT 的演示。

场景由 `Code/scripts/make_pile_scene.py` 按固定种子生成，可完全复现；
生成时直接检查物体间距，不会违反"禁止初始互相嵌入"的约束。

## 9. 接口

新增两个 `simulation` 字段（`docs/02_场景JSON规范.md` 有完整说明）：

| 字段 | 默认 | 说明 |
|---|---|---|
| `broadphase` | `"spatial_hash"` | `"spatial_hash"` 或 `"brute"`（后者用于对照） |
| `broadphase_cell_size` | `0.0` | 0 表示按物体尺寸自动估算 |

诊断量：

```python
world.last_candidate_count   # 最近一次宽阶段产生的候选对数
world.broadphase.stats       # {"cells": ..., "large": ..., "pairs": ...}
```

`detect_contacts(bodies, ground, candidate_pairs)` 的第三个参数是可选的：
传 `None` 退化为暴力枚举，保留给对照实验。

**输出顺序与暴力路径逐位一致**——候选对按第一个下标分组、组内升序，再按 `i` 升序遍历，
于是"地面接触 + 物体对"的交错顺序与暴力路径完全相同。这一点很重要：
如果只是简单遍历候选对列表，顺序会变，求解器的迭代次序随之改变，
数值上出现微小差异，让加速比对照失去意义。

## 10. 遗留

| 问题 | 现状 |
|---|---|
| 格子边长固定 | 物体尺寸差异极大时不是最优；可考虑多级网格 |
| 无增量更新 | 每步清空重建，简单但有小常数开销 |
| 无 SAP / BVH 对照 | 只比了暴力基线，没和扫描-剪枝（SAP）比 |
| 宽阶段不影响 TOI | `earliest_toi` 仍是 O(N²)，在物体多时成为新瓶颈 |
